# Εικόνα από Hikvision μέσω HTTP (για developers)

Πώς παίρνουμε ζωντανή εικόνα από καταγραφικό Hikvision **χωρίς RTSP**, και πώς
πιάνουμε 15+ fps. Χρήσιμο όταν η ροή RTSP είναι κρυπτογραφημένη από το
Hik-Connect (δες `../../ΟΔΗΓΟΣ_ΕΙΚΟΝΑΣ.md`) ή όταν θέλεις απλό JPEG χωρίς
αποκωδικοποιητή H.264/H.265.

## Περιεχόμενα φακέλου

| Αρχείο | Τι είναι |
|---|---|
| `hik_http_client.py` | Αυτόνομος πελάτης (standard library μόνο). Βιβλιοθήκη + CLI για μέτρηση fps. |
| `mock_dvr.py` | Ψεύτικο καταγραφικό με Digest + keep-alive, για δοκιμές χωρίς συσκευή. |

## Τα δύο endpoints του ISAPI

Και τα δύο γυρνούν JPEG που φτιάχνει το καταγραφικό, σε δρόμο που **δεν**
επηρεάζεται από την κρυπτογράφηση ροής:

```
GET /ISAPI/Streaming/channels/<id>/picture       -> ένα JPEG (polling)
GET /ISAPI/Streaming/channels/<id>/httpPreview    -> multipart/x-mixed-replace (MJPEG)
```

`<id>` = κανάλι × 100 + τύπος ροής. Π.χ. κάμερα 1 κύρια = `101`, sub = `102`.
Οι IP κάμερες αριθμούνται από `ip_base + N` (συνήθως 16 ή 32).

Το `httpPreview` δεν υπάρχει σε όλα τα firmware. Ο πελάτης το δοκιμάζει πρώτο
και, αν δεν απαντήσει με `multipart`, πέφτει αυτόματα σε polling στο `picture`.

## Γιατί πιάνουμε υψηλά fps: keep-alive + χειροκίνητο Digest

Η συνηθισμένη προσέγγιση (π.χ. `urllib` με έναν handler ανά αίτημα) πληρώνει σε
**κάθε καρέ**: νέο TCP handshake, και τον γύρο Digest 401 → υπολογισμός → 2ο
αίτημα. Σε ένα DVR με ~30-50 ms latency ανά round-trip, αυτό ρίχνει το ταβάνι
πολύ κάτω από τα 15 fps.

Η λύση (`DigestKeepAliveClient`):

1. **Μία μόνιμη σύνδεση** (`Connection: keep-alive`) ανά κάμερα. Το TCP
   handshake γίνεται μία φορά.
2. **Το Digest challenge αποθηκεύεται** μετά το πρώτο 401. Κάθε επόμενο αίτημα
   στέλνει έτοιμο `Authorization` με αυξανόμενο `nc`, οπότε κοστίζει **ένα**
   round-trip, όχι δύο.

Έτσι κάθε καρέ = ένα request/response στην ίδια σύνδεση. Ο υπολογισμός Digest
(RFC 2617, qop=auth):

```
HA1      = MD5(username : realm : password)
HA2      = MD5("GET" : uri)
response = MD5(HA1 : nonce : nc : cnonce : "auth" : HA2)
```

Το `nonce`, `realm`, `opaque` έρχονται από το `WWW-Authenticate` του 401. Το
`cnonce` το φτιάχνουμε μία φορά, το `nc` αυξάνει σε κάθε αίτημα. Αν το DVR
απαντήσει ξανά 401 (παλιό nonce), ξαναδιαβάζουμε το challenge και συνεχίζουμε.

## Έλεγχος τι υποστηρίζει το καταγραφικό

```bash
python hik_http_client.py --ip <IP> --user admin --password <pass> --channel 1 --probe
```
Δείχνει, για κάθε endpoint, status + content-type + λόγο αποτυχίας. Προσοχή:
πολλά Turbo HD (π.χ. DS-7216HUHI-K2, firmware V4.21.x) **δεν υποστηρίζουν MJPEG**
και απαντούν `403 - invalidOperation` στο `httpPreview`. Τότε μένει μόνο το
polling στο `picture`.

Ταβάνι του polling σε μία κάμερα (καρέ όσο πιο γρήγορα γίνεται):
```bash
python hik_http_client.py --ip <IP> --user admin --password <pass> --channel 1 --bench
```
Τυπώνει fps, και χρόνο ανά καρέ (διάμεσος/p90) - το όριο το βάζει το latency
δικτύου + ο χρόνος που θέλει το DVR να φτιάξει κάθε JPEG.

## Αν τα fps είναι χαμηλά: `--sweep`

```bash
python hik_http_client.py --ip <IP> --user admin --password <pass> --channel 1 --sweep
```
Δοκιμάζει 5 δρόμους εικόνας (κύρια/sub ροή, μικρότερες αναλύσεις, χωρίς ISAPI)
και μετά τον καλύτερο με 1-6 **παράλληλες συνδέσεις στην ίδια κάμερα**.

- Αν τα fps συνολικά **ανεβαίνουν** με τις συνδέσεις, το DVR εξυπηρετεί
  παράλληλα: ο πελάτης μπορεί να ανοίξει πολλές συνδέσεις ανά κάμερα και να πάρει
  περισσότερα καρέ (το καθένα ακόμα αργό, αλλά πολλά μαζί).
- Αν μένουν **σταθερά**, το DVR φτιάχνει μία εικόνα τη φορά και αυτό είναι το
  όριο της συσκευής (1000 / ms-ανά-καρέ).

Το `mock_dvr.py --serial` μιμείται το δεύτερο σενάριο για δοκιμές.

## Πολλές παράλληλες συνδέσεις ανά κάμερα (το κόλπο για περισσότερα fps)

Σε DVR που φτιάχνει κάθε JPEG σε π.χ. 350 ms, μία σύνδεση δίνει ~3 fps. Αν το DVR
εξυπηρετεί αιτήματα **παράλληλα** (το `--sweep` το δείχνει), ανοίγουμε N συνδέσεις
στην ίδια κάμερα, μετατοπισμένες στον χρόνο, και κρατάμε πάντα το νεότερο καρέ
(παλιότερο που ήρθε αργότερα πετιέται, ώστε η εικόνα να μην πηγαινοέρχεται).

Μέτρηση σε πραγματικό DS-7216HUHI-K2 (κανάλι 3, ανάλυση 352x288):

| συνδέσεις | 1 | 2 | 3 | 4 | 6 |
|---|---|---|---|---|---|
| fps συνολικά | 2.7 | 5.7 | 7.7 | 8.1 | 9.7 |

Το κέρδος μικραίνει μετά τις ~3-4 συνδέσεις (το DVR φτάνει στο όριό του).
Η μικρότερη ανάλυση (`?videoResolutionWidth=352&videoResolutionHeight=288`)
έριξε τον χρόνο ανά καρέ από 565 σε 342 ms.

## Δοκιμή χωρίς συσκευή

```bash
# τερματικό 1: ψεύτικο DVR (20 ms ανά εικόνα ~ ταβάνι 50 fps, με MJPEG)
python mock_dvr.py --port 8080 --jpeg καποια.jpg --delay 0.02 --mjpeg

# τερματικό 2: μέτρηση
python hik_http_client.py --ip 127.0.0.1 --port 8080 --user admin --password test \
       --channel 1 --fps 15 --seconds 10 --save frame.jpg
```

## Μετρήσεις στο ψεύτικο DVR

Mock με καθυστέρηση 20-40 ms ανά εικόνα, μία κάμερα, localhost:

| Τρόπος | Ζητούμενο | Αποτέλεσμα |
|---|---|---|
| polling | 15 fps | **15.0 fps** |
| polling | 30 fps | 15.6 fps (όριο ο χρόνος δημιουργίας εικόνας) |
| MJPEG | — | **24.7 fps** |

Η μόνιμη σύνδεση επαναχρησιμοποιείται: στη ροή MJPEG όλη η δουλειά έγινε με
**1 σύνδεση**. Σε πραγματικό DVR ο ρυθμός εξαρτάται από το latency του δικτύου
και το πόσο γρήγορα φτιάχνει εικόνες το καταγραφικό.

## Πώς να πας ακόμη πιο ψηλά

- **MJPEG αντί για polling** όπου υπάρχει: μία σύνδεση, το DVR σπρώχνει καρέ με
  τον δικό του ρυθμό. Ο ρυθμός ακολουθεί τα **fps της sub ροής** — ανέβασέ τα
  στο DVR (Βίντεο → Δευτερεύουσα ροή → Ρυθμός Καρέ 15-25).
- **Μικρότερη ανάλυση / ποιότητα** στη sub ροή: μικρότερα JPEG = λιγότερος
  χρόνος δημιουργίας και μεταφοράς ανά καρέ.
- **Μία σύνδεση ανά κάμερα, σε δικό της νήμα** (όπως εδώ): οι κάμερες τρέχουν
  παράλληλα, δεν περιμένει η μία την άλλη.
- **Ενσύρματο δίκτυο, ίδιο switch** με το DVR: ρίχνει το latency ανά round-trip,
  που είναι το βασικό όριο στο polling.

## Όρια

- Πολλές κάμερες ταυτόχρονα σε υψηλά fps ζορίζουν το DVR (π.χ. 16 × 15 fps =
  240 εικόνες/s — δύσκολα). Κράτα χαμηλά fps στο πλέγμα, υψηλά σε μονή προβολή.
- Δεν υπάρχει ήχος, και η ποιότητα είναι JPEG (όχι πλήρες βίντεο H.264/H.265).
  Για πλήρη ροή πρέπει να κλείσει η κρυπτογράφηση στο DVR.
