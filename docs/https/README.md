# HTTPS προς καταγραφικό Hikvision (για developers)

Πώς μιλάμε με το καταγραφικό (ISAPI) μέσω **HTTPS** αντί για απλό HTTP, με
αυτο-υπογεγραμμένο πιστοποιητικό, και πώς προστατευόμαστε από πλαστό καταγραφικό.

> **Κατάσταση:** η υλοποίηση έχει δοκιμαστεί με ψεύτικο καταγραφικό (`docs/http/mock_dvr.py --tls`)
> και με σενάρια αποτυχίας (κλειστή θύρα, κομμένο handshake, αλλαγή πιστοποιητικού).
> **Δεν έχει δοκιμαστεί ακόμα σε πραγματικό DS-7216HUHI-K2** — εκεί το HTTPS ήταν ανενεργό
> (θύρα 443 κλειστή). Μετά την ενεργοποίησή του, τρέξε το `hik_https_check.py` (βλ. παρακάτω).

## Περιεχόμενα φακέλου

| Αρχείο | Τι είναι |
|---|---|
| `hik_https_client.py` | Αυτόνομος πελάτης (standard library μόνο): TLS keep-alive + Digest + pinning πιστοποιητικού. Βιβλιοθήκη και CLI. |
| `hik_https_check.py` | Διαγνωστικό: δοκιμάζει ένα-ένα τα στάδια (θύρα → TLS → πιστοποιητικό → αίτημα). |
| `../http/mock_dvr.py --tls` | Ψεύτικο καταγραφικό με HTTPS για δοκιμές (χρειάζεται `pip install cryptography`). |

Στο viewer ο αντίστοιχος κώδικας είναι στο `hik_rtsp_viewer.py`: `_tls_context`, `CERT_PINS`,
`CertChangedError`, `FastHttpClient._check_pin`, `describe_net_error`.

## Σχεδιασμός

### 1. Γιατί δεν κάνουμε κανονική επαλήθευση πιστοποιητικού

Τα καταγραφικά έχουν **αυτο-υπογεγραμμένο** πιστοποιητικό: καμία αρχή πιστοποίησης δεν το έχει
υπογράψει και το όνομά του (συνήθως η IP) δεν ταιριάζει με κάποιο domain. Ο συνηθισμένος έλεγχος
θα απέρριπτε πάντα τη σύνδεση. Αν όμως τον απενεργοποιήσουμε χωρίς τίποτα άλλο, η κρυπτογράφηση
δεν προστατεύει από man-in-the-middle. Γι' αυτό:

```python
ctx.check_hostname = False
ctx.verify_mode = ssl.CERT_NONE        # + έλεγχος αποτυπώματος (pin) αμέσως μετά το handshake
```

### 2. Trust on first use (TOFU) με pin

Μετά το handshake παίρνουμε το πιστοποιητικό (`sock.getpeercert(binary_form=True)`, DER) και το
αποτύπωμά του (SHA-256) συγκρίνεται με αυτό που έχουμε αποθηκεύσει για το `host:port`:

| Κατάσταση | Αποτέλεσμα |
|---|---|
| Δεν υπάρχει pin | Αποθηκεύεται, η σύνδεση συνεχίζει (`"new"`) |
| Ίδιο αποτύπωμα | Συνεχίζει (`"ok"`) |
| Διαφορετικό | Κλείνει τη σύνδεση και σηκώνει `CertChangedError` — **δεν στέλνεται ούτε ο κωδικός** |

Ο έλεγχος γίνεται **πριν** σταλεί οτιδήποτε αίτημα, άρα ένας πλαστός server δεν παίρνει ούτε
το Digest response. Το pin αποθηκεύεται σε JSON (`PinStore`, ατομική εγγραφή με `os.replace`).

**Όρια του TOFU:**
- Η *πρώτη* σύνδεση εμπιστεύεται ό,τι δει. Κάν' την από αξιόπιστο δίκτυο.
- Αν ξαναδημιουργηθεί το πιστοποιητικό (νέο firmware, νέα δημιουργία στο DVR) το pin πρέπει να
  γίνει reset συνειδητά (`--reset-pin` / `PinStore.forget`). Μην το αυτοματοποιείς.

### 3. Συμβατότητα με παλιά firmware (και τι κοστίζει)

Τα παλιά Hikvision (π.χ. V4.21.x του 2020) μπορεί να έχουν TLS 1.0/1.1 και πιστοποιητικά
RSA-1024/SHA-1. Η σύγχρονη Python/OpenSSL 3 τα απορρίπτει εξ ορισμού. Το `tls_context(legacy=True)`:

```python
ctx.minimum_version = ssl.TLSVersion.TLSv1       # κρύβουμε το DeprecationWarning με warnings.catch_warnings
ctx.set_ciphers("ALL:@SECLEVEL=0")               # fallback: "DEFAULT:@SECLEVEL=0"
```

Αυτό **χαλαρώνει** την ασφάλεια (ασθενή κρυπτοσυστήματα, παλιά πρωτόκολλα) — με το pin το ρίσκο
περιορίζεται, αλλά όχι εξαφανίζεται. Αν το καταγραφικό σου έχει σύγχρονο TLS 1.2+, χρησιμοποίησε
`legacy=False` / `--no-legacy-tls`.

### 4. Digest πάνω από μόνιμη σύνδεση

Ίδια λογική με το `docs/http/`: ένα handshake TLS ανά κάμερα (το ακριβό μέρος), αποθηκευμένο
Digest challenge, αυξανόμενο `nc`, ένα round-trip ανά αίτημα. Αν η σύνδεση κλείσει, ξανασυνδέεται
μία φορά (και ξανακάνει έλεγχο pin).

## Χρήση

```python
from hik_https_client import DigestHttpsClient, PinStore, CertChangedError

pins = PinStore("pins.json")
c = DigestHttpsClient("https://192.168.1.64:443/ISAPI/Streaming/channels/101/picture",
                      "admin", "pass", pins)
try:
    jpeg = c.get()            # bytes
except CertChangedError as e:
    ...                       # ΜΗΝ συνεχίσεις· ειδοποίησε τον χρήστη
```

CLI:
```bash
python hik_https_client.py --ip 192.168.1.64                 # model/firmware + κατάσταση pin
python hik_https_client.py --ip 192.168.1.64 --picture 1 --save a.jpg
python hik_https_client.py --ip 192.168.1.64 --bench --seconds 10
python hik_https_client.py --ip 192.168.1.64 --reset-pin
```
Ο κωδικός από `--password` ή τη μεταβλητή `HIK_PASSWORD` (προτίμησε τη μεταβλητή).

## Ενεργοποίηση HTTPS στο καταγραφικό

Στο DS-7216HUHI-K2 (web V4.0.1) βρίσκεται στο **Δίκτυο → Προηγμένες ρυθμίσεις → Υπηρεσία δικτύου**.
Το «Ενεργοποίηση HTTPS» είναι γκρι ώσπου να υπάρξει πιστοποιητικό:

1. «Μέθοδος εγκατάστασης» → **«Δημιουργία αυτο-υπογεγραμμένου πιστοποιητικού»** (η **πρώτη**
   επιλογή) → κουμπί **«Δημιουργία»**.
2. Φόρμα: **Χώρα** = `GR`, **IP / Όνομα Domain** = η IP του καταγραφικού (δεν χρειάζεται domain).
   Τα υπόλοιπα είναι προαιρετικά.
3. Τσέκαρε «Ενεργοποίηση HTTPS» → Αποθήκευση. Η θύρα ορίζεται στο **Δίκτυο → Θύρα**.

**Προσοχή:** η *τρίτη* επιλογή («Δημιουργήστε πρώτα την αίτηση πιστοποιητικού…») φτιάχνει μόνο
αίτηση (CSR) για εξωτερική αρχή και **δεν** δίνει πιστοποιητικό που δουλεύει από μόνο του.
Η αποθήκευση μπορεί να ξαναρχίσει την υπηρεσία web — κάν' το σε ώρα χαμηλής κίνησης.

## Διάγνωση

```bash
python hik_https_check.py                       # από τη ρίζα του repo (ή docs/https/hik_https_check.py)
python hik_https_check.py --ip 192.168.35.18 --port 443
```

| Σύμπτωμα | Πιθανή αιτία |
|---|---|
| `ConnectionRefusedError` | Η υπηρεσία HTTPS δεν είναι ενεργή στο καταγραφικό (η θύρα 443 είναι **γραμμένη** στις ρυθμίσεις αλλά κλειστή) |
| `TimeoutError` | Λάθος IP, firewall, ή το καταγραφικό δεν φτάνεται |
| `ConnectionResetError` κατά το handshake | Το καταγραφικό δεν δέχεται το προτεινόμενο TLS/κρυπτοσύστημα, ή δεν είναι HTTPS η θύρα |
| `SSLError … UNEXPECTED_EOF` | Όπως παραπάνω: κόβει τη σύνδεση στο handshake |
| `SSLError … PROTOCOL_VERSION` | Δοκίμασε `legacy=True` (παλιό TLS) |
| `CertChangedError` | Άλλαξε το πιστοποιητικό: νέο firmware/νέα δημιουργία, **ή πλαστό καταγραφικό** |
| `HTTP 401/403` | Λάθος χρήστης/κωδικός, ή «Έλεγχος ταυτότητας WEB» δεν είναι `digest` (Μπορεί `digest` ή `digest/basic`· ο πελάτης μιλά μόνο Digest) |

Το διαγνωστικό δοκιμάζει TLS 1.3, 1.2, 1.1, 1.0 ξεχωριστά και δείχνει ποια δουλεύει, και τυπώνει
αποτύπωμα, αλγόριθμο υπογραφής και μέγεθος κλειδιού του πιστοποιητικού.

## Δοκιμή χωρίς συσκευή

```bash
pip install cryptography
python ../http/mock_dvr.py --port 8443 --jpeg εικόνα.jpg --tls     # νέο πιστοποιητικό σε κάθε εκκίνηση
python hik_https_client.py --ip 127.0.0.1 --port 8443 --user admin --password test --picture 1
```
Ξανακάνε εκκίνηση του mock → νέο πιστοποιητικό → ο πελάτης πρέπει να αρνηθεί (`CertChangedError`),
που δείχνει ακριβώς τι θα γινόταν με πλαστό καταγραφικό.

## Όρια και προτάσεις

- Μόνο snapshot/ISAPI μέσω HTTPS. Το **RTSP δεν** περνά από εδώ (και η ροή RTSP αυτού του
  καταγραφικού είναι ούτως ή άλλως κρυπτογραφημένη από το Hik-Connect).
- Το MJPEG (`httpPreview`) δεν υποστηρίζεται στο συγκεκριμένο firmware.
- Για πρόσβαση **από το internet** μην ανοίγεις θύρα στο router· χρησιμοποίησε **VPN** προς το
  τοπικό δίκτυο και συνέχισε να μιλάς με την τοπική IP.
